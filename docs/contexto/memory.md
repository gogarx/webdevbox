# Memória — Registro Cronológico de Decisões e Correções

Este arquivo é a memória viva do projeto: toda decisão relevante, todo erro persistente e toda correção manual devem ser registrados aqui, em ordem cronológica, para que nenhuma sessão futura precise redescobrir o que já foi resolvido. O registro começa na sessão de 10 de outubro de 2026, quando o ambiente foi estabilizado do build ao terminal.

## 10 de outubro de 2026 — Sessão de estabilização completa

**Ambiente do host:** BigLinux Nativo, kernel Xanmod LTS 6.18, GPU NVIDIA 940MX. Host baseado em Manjaro, com Podman em `/usr/share/containers/` seguindo o empacotamento novo do containers-common.

**Primeira batalha — o build que falhava no LunarVim (STEP 11/28):** o `podman build` quebrava com `exit status 1` no passo do instalador do LunarVim, e a causa raiz estava três estágios antes, disfarçada. No estágio 1, o `pacman -Syyu` abortava a transação inteira com `error: target not found: zsh-theme-powerlevel10k-git` — um pacote que só existe no AUR, jamais nos repositórios oficiais — e, como o pacman aborta tudo quando um alvo não existe, nenhum dos ~70 pacotes da lista era instalado. O encadeamento com ponto e vírgula mascarava a falha: `archlinux-java` dava `command not found`, o `pacman -Rns $(pacman -Qtdq)` reclamava `no targets specified`, e ainda assim o RUN terminava com exit 0. Lá na frente, o instalador do LunarVim procurava `fd`, `rg` e o fallback `cargo` — todos ausentes porque nunca foram instalados — e abortava. A correção foi reescrever o bloco de instalação removendo o pacote AUR-only da lista, encadeando com `&&` para falhar rápido, adicionando `--needed` para não reinstalar pacotes atualizados, e protegendo a remoção de órfãos com `{ pacman -Rns --noconfirm $(pacman -Qtdq) || echo "Nothing to remove"; }`, tudo num único RUN para não estourar as camadas.

**Segunda batalha — o storage.conf desaparecido (STEP 24/28):** com o LunarVim finalmente passando, o build avançou até o passo que configura o podman interno e falhou com `sed: can't read /etc/containers/storage.conf: No such file or directory`. O containers-common do podman 5.x não instala mais esse arquivo em `/etc/containers` — o template oficial agora vive em `/usr/share/containers/storage.conf`. A correção copiou o template quando o arquivo não existe (`test -f ... || cp ...`) e reescreveu os padrões do sed para o formato novo do template, pois o antigo append de `additionalimagestores` geraria TOML inválido e o padrão de `ignore_chown_errors` não casava mais com a nova sintaxe com aspas. Resultado: `mount_program` apontando para `fuse-overlayfs`, `additionalimagestores = ["/var/lib/shared"]`, `mountopt = "nodev,fsync=0"` e `ignore_chown_errors = "true"`. O build completou: imagem `localhost/akitaonrails/webdevbox:latest` (ID `8d8ff97706fc`, 10.7 GB), com o log completo preservado em `arquivos.txt`.

**Terceira batalha — o resgate do esqueleto:** ao entrar no contêiner via Distrobox, o LunarVim e o asdf não estavam na home do usuário, porque o Distrobox não herda os arquivos que o root gerou no `/etc/skel/` durante o build. Foi feito o resgate manual do esqueleto — `.local/share/lunarvim`, o binário `lvim`, o `config.lua` e a árvore `.asdf` — copiando de `/etc/skel/` para a home de `gogarx` e corrigindo as permissões com `chown`. A home interna foi redirecionada para `/mnt/HD_GOGARX/Dev/home_webdevbox` (HDD 1TB, Btrfs com ZSTD), protegendo o SSD principal do I/O de caches e compilações.

**Quarta batalha — os alertas de migração e o asdf reescrito em Go:** o LunarVim abria com alertas vermelhos de migração, e a causa era dupla. Primeiro, removemos o source do script antigo `asdf.sh` do `/etc/profile` e do `~/.zshrc`, porque as versões recentes do Arch reescreveram a ferramenta nativamente em Go e o binário agora vive direto em `/usr/bin/asdf` — o script legacy só gerava ruído e risco de PATH quebrado. Segundo, limpamos os alertas restantes substituindo globalmente a sintaxe obsoleta `requires` por `dependencies` dentro da tabela `lvim.plugins` no arquivo `config.lua`, alinhando a configuração com a API nova do lazy.nvim.

**Quinta batalha — o erro fatal do vim-illuminate:** a sincronização de plugins travava com o erro fatal `attempt to call method 'parent'` disparado pelo plugin `vim-illuminate`, provocado por mudanças na API de nós do Neovim moderno que o snapshot antigo do plugin não suportava. A resolução foi sincronizar os plugins pelo barramento do GitHub (forçando o download das versões novas, já com o patch do upstream) e, em seguida, rodar em série os comandos `:MasonUpdate`, `:Lazy sync` e `:TSUpdate` dentro do LunarVim, que atualizaram respectivamente os servidores de linguagem, os plugins e os parsers de Treesitter. Com isso o editor estabilizou: abre limpo, sincroniza sem erros e os alertas vermelhos sumiram.

**Sexta batalha — o polimento do terminal:** o terminal abria com o logotipo ASCII do BigLinux que o `ble.sh` injeta via `/etc/bigblerc`, poluindo a abertura do Zsh. A solução foi adicionar a flag de desativação no `~/.blerc` do usuário, o que silencia o logo sem mexer no arquivo de sistema. E o encurtamento feio de diretórios no Powerlevel10k — caminhos truncados de forma confusa no prompt — foi corrigido mudando a estratégia em `~/.p10k.zsh` para `truncate_with_ellipsis` com o comprimento fixado em 2, mantendo os caminhos curtos, legíveis e com reticências elegantes.

**Sétima batalha — o pino duplo do Neovim e do LunarVim (13/10/2026, Tarefa 3 da fila):** a imagem v1 trazia o Neovim mais recente dos repositórios do Arch (0.12.5), que quebra o LunarVim com o erro de tree-sitter `query_predicates` na inicialização. A decisão foi fixar o Neovim em 0.9.5 via tarball oficial do GitHub, extraído em `/opt/nvim-linux64` com symlink em `/usr/local/bin/nvim`, removendo o `neovim` das listas do pacman no estágio 1 e no STEP 11 e usando o `ARG NEOVIM_VERSION=0.9.5` no lugar do `0.9`. O primeiro rebuild revelou que o instalador do LunarVim **master** recusa Neovim anterior a 0.10 ("Please upgrade your Neovim base installation"), então fixamos também o LunarVim no branch estável `release-1.3/neovim-0.9` via env `LV_BRANCH`, aproveitando o `ARG LUNARVIM_VERSION=1.3` que existia sem uso — esse branch é o emparelhamento oficial 1.3 + Neovim 0.9, exatamente a era que o `helpers/config.lua` e a home persistida usam. O segundo rebuild revelou que, em modo não interativo, o `install.sh` roda com `set -eo pipefail` e chama `install_python_deps` sem guarda: sem pip no sistema e com o `ensurepip` bloqueado pelo PEP 668 do Arch (`externally-managed-environment`), o script morria silenciosamente com exit 1 logo após o WARN de python. Testes em container efêmero provaram que o env `PIP_BREAK_SYSTEM_PACKAGES=1` não é respeitado pelo bootstrap do ensurepip do pip 26, mas funciona numa invocação normal do pip, então a correção final foi instalar `python-pip` via pacman no STEP 11 (fazendo o check `pip --version` passar, já que a falha do ensurepip é tolerada) e exportar `PIP_BREAK_SYSTEM_PACKAGES=1` na invocação do instalador para liberar o `pip install --user pynvim`. O terceiro build ficou verde: COMMIT `e3dab9806087` (10.8 GB), bootstrap do Lazy completo, verificação de plugins completa, e o smoke test com um usuário recém-criado herdando o `/etc/skel` mostrou `lvim --headless +qa` com exit 0, saída vazia e nenhum erro de query_predicates. Detalhe para o futuro: o pynvim é instalado em `/root/.local` e não é propagado pelo skel, de modo que o provider python do Neovim segue opcional para os usuários, como sempre foi; e o contêiner de produção `webdevbox-prod` precisa ser recriado sobre a nova imagem para receber o Neovim fixado.

**Oitava batalha — o npm sequestrado, o PATH mutilado e o runtime defasado (13/10/2026):** o LunarVim voltou a travar ao iniciar porque o Mason tentava instalar tailwindcss-language-server, html-lsp e bash-language-server e falhava com "npm is not executable", registrado no mason.log da home persistida. A causa raiz é que o Arch separou o npm do nodejs — o npm agora é um pacote próprio, listado apenas como optdepends — de modo que a imagem tinha nodejs (puxado como dependência do yarn) e yarn, mas nenhum npm, e o instalador do LunarVim nunca notou durante o build porque usa o yarn para seus próprios módulos. A correção na imagem foi adicionar nodejs e npm explícitos à linha pacman do STEP 11; no contêiner de produção, o hot-fix foi `pacman -Sy nodejs npm` como root, a varredura de fantasmas com pkill não encontrou nenhum nvim/lvim vivo (o namespace de PID do Distrobox é compartilhado com o host, e o que aparecia no ps era apenas o kate do host e o nosso próprio build), e a linha `source /opt/asdf-vm/asdf.sh` foi removida do /etc/profile — uma regressão da Quarta Batalha, já que o Dockerfile re-adicionava a linha a cada build e o asdf novo é binário Go em /usr/bin/asdf. O teste de fumaça então expôs duas feridas mais fundas: primeiro, o PATH de login não resolvia o lvim porque o antigo `sed 's/PATH=/PATH=$HOME\/.local\/bin/g'` do STEP 27 mutilara a função `append_path` do /etc/profile, colando `$HOME/.local/bin` sem separador dentro do corpo da função e replicando o lixo quatro vezes a cada shell de login, e porque o perfil moderno do Arch encerra com `unset -f append_path`, invalidando qualquer chamada feita depois dele — a correção restaurou a função no contêiner e passou a inserir `append_path "$HOME/.local/bin"` imediatamente antes da limpeza, e o Dockerfile foi reescrito para fazer exatamente isso, sem o sed destrutivo e sem o source do asdf.sh. Segundo, o runtime do LunarVim da home persistida era um clone da era master, estabilizado em outubro contra o nvim 0.12.5 do contêiner antigo, e recusava o novo nvim 0.9.5 com "requires v0.10+"; seguindo o padrão de resgate da Terceira Batalha, o runtime master foi preservado em `~/.local/share/lunarvim.master.bak` e substituído pelo runtime 1.3 pristine do /etc/skel com chown para gogarx, o lockfile antigo renomeado para lazy-lock.json.bak e o repositório interno liberado no git com safe.directory. A verificação final comprovou a estabilidade: `lvim --headless` com exit 0 e nenhum travamento, e um :MasonInstall headless registrou "Installation succeeded" para os três servidores no mason.log, com os binários presentes em `~/.local/share/lvim/mason/bin`. A imagem definitiva nasceu no commit `17c461984153` (npm 12.2.0, nvim 0.9.5, perfil limpo). Notas para o futuro: o npm 12 bloqueia scripts de pós-instalação por padrão ("install scripts blocked"), o que não impediu os servidores; e sempre que o contêiner for recriado sobre uma imagem nova, a home persistida pode divergir do branch pinado e o resgate do esqueleto do runtime precisa ser reavaliado. **Epílogo da Oitava — o null-ls sequestrado pelo GitHub (14/10/2026):** com o editor destravado, o lazy.nvim passou a falhar ao clonar o null-ls com erro de credenciais ("terminal prompts disabled"), deixando apenas um marcador `null-ls.nvim.cloning` e nenhum clone real — tanto na home persistida quanto no próprio esqueleto da imagem, onde a falha era silenciosa desde o build. O diagnóstico presumido (URL SSH pedindo chaves) estava errado: o spec usa HTTPS e o repositório `jose-elias-alvarez/null-ls.nvim` simplesmente não existe mais no GitHub, e um 404 do GitHub faz o git pedir credenciais — com o GIT_TERMINAL_PROMPT=0 que o lazy impõe, o clone morre. A solução definitiva seguiu a ideia do insteadOf, mas com o alvo correto: `url."https://github.com/nvimtools/none-ls.nvim".insteadOf "https://github.com/jose-elias-alvarez/null-ls.nvim"` — o fork da comunidade clona normalmente e preserva o módulo lua/null-ls, sendo drop-in para o LunarVim 1.3 — mais a linha de higiene `url."https://github.com/".insteadOf "git@github.com:"` para qualquer spec SSH futura. Ambas foram aplicadas no Dockerfile, antes do instalador do LunarVim (valendo para o bootstrap do build), e no ~/.gitconfig do gogarx dentro do contêiner em produção; o marcador corrompido foi removido da home e o teste headless confirmou o null-ls.nvim clonado com o módulo intacto, tanto na home persistida quanto no esqueleto da imagem definitiva (commit `c69f5bddb0b9`).

**Nona batalha — o launcher afogado no esqueleto e o lvim que se auto-executava (14/10/2026):** o launcher do lvim pendurava na abertura com o erro de fifo (`/usr/sbin/distrobox-enter: linha 768: .webdevbox-prod.fifo inexistente`) e o contêiner terminava em Exited 143 após cancelamentos. A primeira causa raiz veio dos logs do init: o distrobox-init percorre o `/etc/skel` arquivo a arquivo a cada boot do contêiner, e o Dockerfile havia plantado lá as árvores pesadas — 677 MB de `.asdf` e 89 MB de lunarvim — tornando cada inicialização uma varredura de muitos minutos; o distrobox-enter do launcher esperava eternamente o `container_setup_done` e o erro do fifo era só o ruído transitório desse caminho (o enter cria o fifo, despeja os logs do podman nele aguardando o sinal do init e o remove depois). A correção de contêiner usou `podman unshare` com `podman container mount` sobre o contêiner parado para apagar as duas árvores do skel via whiteouts da camada gravável — o boot seguinte alcançou `container_setup_done` em 16 segundos — e o STEP 12 do Dockerfile foi reescrito para manter um esqueleto leve de 36 KB (shim lvim e configs) com as árvores pesadas servindo de fonte de resgate em `/opt/webdevbox-defaults`. A segunda causa raiz era pior: o próprio lvim travava na inicialização, e um strace de 45 segundos capturou 4597 chamadas de execve — todas do próprio `~/.local/bin/lvim` — porque a tentativa de `distrobox-export` do usuário havia SOBRESCRITO o shim do LunarVim com um wrapper de exportação cujo ramo dentro do contêiner (`exec` do mesmo caminho) entrava num loop infinito de auto-execução a ~100 vezes por segundo. O shim verdadeiro foi restaurado do `/etc/skel/.local/bin/lvim` (chown para gogarx) e o `lvim --headless +qa` voltou a sair com exit 0 em 3 segundos; um node de LSP órfão com 20 horas de vida foi derrubado pelo lado do host. Descobrimos ainda que o `distrobox-enter -- lvim` executa sem shell de login, então o `~/.local/bin` não existe no PATH dele — a ponte só funcionou depois de plantar o shim também em `/usr/local/bin`, aplicado no contêiner e no Dockerfile (com um `cp` no STEP 12), já que o shim é todo baseado em `$HOME` e serve a qualquer usuário. Por fim o export foi refeito da forma correta, executado via `distrobox-enter` para carregar o ambiente certo: nasceu o `~/.local/share/applications/lvim.desktop` no menu do host (`Exec=distrobox-enter -n webdevbox-prod -- lvim`, Terminal=true) e a ponte foi verificada de ponta a ponta (`lvim --version` → NVIM v0.9.5). A imagem foi reconstruída do zero porque a base archlinux local havia sido re-pulada e bustou toda a cadeia de cache, resultando no commit `e5f6b713c5be` com skel leve, árvores de resgate em `/opt/webdevbox-defaults` e shim em `/usr/local/bin`. Lições para o futuro: nunca apontar `distrobox-export --bin` para o próprio `~/.local/bin/lvim` (o wrapper sobrescreve o alvo e entra em loop dentro do contêiner); qualquer recriação futura do webdevbox-prod sobre a imagem nova herda todas as correções nativamente, sem os hot-fixes de camada gravável. **Encerramento do ciclo (14/10):** o contêiner foi recriado sobre a imagem definitiva e5f6b713c5be com os mesmos parâmetros (`distrobox create --name webdevbox-prod --image localhost/akitaonrails/webdevbox:latest --home /mnt/HD_GOGARX/Dev/home_webdevbox`), o init alcançou `container_setup_done` em segundos sobre o skel leve, e todas as verificações passaram nativamente da imagem: `lvim --headless +qa` com exit 0 como gogarx, npm 12.2.1, as duas regras insteadOf no gitconfig da home persistida, os 4 pacotes Mason intactos, a ponte `distrobox-enter -- lvim --version` retornando NVIM v0.9.5 e os launchers `lvim.desktop` e `webdevbox-prod.desktop` presentes no menu do host. Nota de manutenção: o novo contêiner tem `Config.User root:root`, portanto `podman exec` sem `-u` roda como root — em auditorias usar `podman exec -u gogarx` (o `distrobox enter` e o launcher forçam o usuário e não são afetados). Por fim, mais de 250 intermediários de build foram podados com `podman image prune` e a imagem upstream de 3 anos foi removida, levando o armazenamento de imagens de 80,36 GB para 10,04 GB — o cache de build foi consumido de propósito, então o próximo `podman build` sai do zero (~40 min).
